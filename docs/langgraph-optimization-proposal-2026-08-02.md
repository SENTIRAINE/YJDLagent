# LangGraph 最小优化提案

日期：`2026-08-02`  
依据：`spring-comprehensive-test-report-2026-08-02.md` 的真实用户与老年语言场景  
范围：只提出 LangGraph 侧优化，不修改 Spring Tool 的业务计算和数据契约

## 1. 目标与边界

本轮 12 个自然语言场景中，U01、U06、U08 进入非澄清路径，9 个进入 `CLARIFY`。Spring 的 A01-A11、真实 GeoScene 数据、SSE 传输与地图绘制已经独立通过，因此最小优化目标是让 LangGraph 更稳定地把普通用户，尤其老年用户的口语需求映射到现有 Tool，而不是扩展新的 Spring 能力。

LangGraph 必须遵守：

- 不自行查询 GeoScene。
- 不重算价格、便利度、道路 WS、百分位、距离、buffer 或推荐分。
- 不补造 Tool 没有返回的字段。
- 不改变 Catalog `2026-07-29.1`、OpenAPI v1.1 或现有 SSE 信封。

## 2. P0：硬条件必须无损进入 Tool

证据：U01“中山区房价不超过一万五，便利一点”调用了 `searchHousingCandidates`，但结果包含 19027 元/㎡房源，`appliedFilters` 为空；同一能力在 Spring A01 独立验收中能正确执行价格硬过滤。

要求：

1. “不超过、以内、最多、别过”等价格上限表达必须映射为 `hardFilters.priceMax`。
2. Tool 调用前对 Planner 输出做确定性校验：原句含明确价格上限但 arguments 没有 `priceMax` 时，不得继续执行为无价格条件查询。
3. 回答只可基于 Tool 的 `resolvedCriteria`、`appliedFilters` 和结果；不得在条件未应用时把结果描述为满足条件。

验收：

- “中山区房价不超过一万五，便利一点”只返回 `price <= 15000` 的住宅。
- `appliedFilters` 明确包含地区、价格上限和实际偏好。
- 一个逻辑需求只调用一次 `searchHousingCandidates`。

## 3. P0：回答必须与已返回的地图证据一致

证据：U06“道路步行指数高点附近有啥小区，百来米就行”已经返回 5 个 resultSet、5 个 overlay，并在浏览器绘制 20 住宅、30 道路、5 缓冲区；文本回答仍称“资料和地图结果不足”。

要求：

1. 回答生成器必须读取同一次 Run 的 `map.result` 和 Tool 摘要，不能仅依赖 RAG 是否有文档。
2. 有住宅候选时说明候选、使用的道路/距离条件和截断警告；没有住宅但有道路/缓冲时说明空住宅结果，不得笼统称“无证据”。
3. 最终回答中的数量、条件和警告必须能追溯到事件 payload，不得自由改写为矛盾结论。

验收：U06 的回答至少说明实际 100 米默认/解析距离、住宅候选数量、道路证据和结果截断情况，并与地图图层计数一致。

## 4. P1：减少对已有默认语义的重复追问

证据：

- U02 已给出 1.2 万/㎡和走路方便，却追问区域；契约规定未指定区域时 `districts=[]`。
- U09 追问“便利度”含义；当前业务语义已固定为 `归一化总分`。
- U12“便宜，好走路”追问找房子还是道路；产品入口和表达语境指向住宅推荐，现有 Tool 支持价格与道路步行软偏好。

要求：

| 用户表达 | 默认解释 |
| --- | --- |
| 未指定行政区 | 全支持区域，`districts=[]` |
| “便宜一点”但无数字 | `price=PREFER_LOW`，不猜 `priceMax` |
| “便利度高一点” | `convenience=PREFER_HIGH`，字段为 `归一化总分` |
| “路好走/走路方便” | `roadWalkability=PREFER_HIGH` |
| “附近/百来米” | 使用契约允许的默认或可确定距离，不把口语当未知指标 |

只有当缺失信息会改变硬约束、对象类型确实无法从当前产品上下文判断，或用户表达超出 Catalog 能力时才进入 `CLARIFY`。

验收：U02、U09、U12 应进入 `MAP_QUERY` 并调用 `searchHousingCandidates`；不得编造总价到单价换算。

## 5. P1：老年人口语、赘词与轻微错别字归一化

覆盖语料：

- “我年纪大了腿脚不好”“我和老伴住”。
- “那个啥”“嗯……那个……”。
- “中山去”“一万五一内”“步行指树”。
- “便宜点儿”“百来米”“住着省心”。

要求：在意图路由前完成保守归一化，保留数字、单位、否定词和上限词；同音/近形纠错只有在领域词典存在唯一高置信候选时应用。归一化结果、原文和最终 Planner arguments 都应进入 trace，方便判断是识别问题还是参数构造问题。

验收：

- U05 能把“中山去 / 一万五一内 / 步行指树”识别为中山区、15000 上限和道路步行偏好。
- 归一化不得把“总预算 200 万”转换成每平方米价格，也不得自行猜面积。

## 6. P1：模型终端失败与部分结果状态

证据：浏览器重复 U06 时出现两次“模型服务暂时无法完成请求”；其中一次 traceId 为 `0f1cbbd6-d4e7-4b4f-8a32-c32c452aca22`。失败前 Spring 已通过 HTTP 200 SSE 传送地图结果，前端完成 20 住宅、30 道路、5 缓冲区绘制。

要求：

1. 记录模型阶段名称、模型请求标识、耗时、错误类型和 retryable 属性，并与 Spring traceId/runId 对齐。
2. 一个 Run 仍只能有一个终态；已有 `map.result` 后模型失败时，终态必须明确表达“地图部分结果已产生、回答生成失败”，不能让客户端误以为地图也失败。
3. 重试必须受 Run 剩余预算和消息幂等约束，不能重复调用已经成功的 Spring Tool。

验收：注入回答模型失败后，Tool 调用次数仍为 1，已有 map.result 可重放，终态错误包含稳定分类且不产生第二终态。

## 7. P2：非专业知识解释保持现有有效路径

证据：U08“步行指数是啥意思？我看不懂”正确进入 `RAG_QA`，返回引用并用 0-100 分区间解释，属于可保留的有效行为。

要求：继续使用短句、先结论后细节、解释指标局限；引用必须对应实际检索文档。不得把知识解释请求错误路由为地图查询，也不得把 RAG 解释用于替代 Tool 的实时业务结果。

## 8. 最小验收集

LangGraph 优化完成必须重放：

1. U01、U02、U05、U06、U08、U09、U12 七个核心场景。
2. U10 总预算口径不明确和 U11 高度含糊继续合理澄清。
3. U07 10000 米不得被静默截断到 2000 米，应澄清或返回稳定参数错误。
4. 每案保存原始请求、Planner 结构、Tool 请求/响应、原始 SSE、traceId/runId、Tool 次数和最终判定。
5. 所有地图查询核对 `appliedFilters`、结果最大/最小价格、图层数量、warnings 与最终回答的一致性。

建议发布门禁：上述核心场景全部符合契约；明确可执行需求不再因缺少行政区或已有默认业务语义而澄清；任何硬价格条件遗漏、地图/文本矛盾或重复 Tool 调用都阻止发布。
